Train/serve skew fix (2026-07-03): on the detector's OWN crops (what production
sees) the classifier improved 76.91% -> **88.88%** while clean-crop accuracy
*rose* to 93.77%. A crops-only fine-tune was auto-rejected for forgetting
(GT fell to 83%) - the promote gate is itself demo-worthy rigor.

### Detector (Stage 1, YOLO26n, 6 classes) — baseline vs retrained
| Model | P | R | mAP50 | mAP50-95 |
|---|---:|---:|---:|---:|
| 30-epoch baseline (val) | 0.757 | 0.592 | 0.672 | 0.505 |
| 100-epoch retrain (val) | 0.788 | 0.634 | 0.707 | 0.536 |
| **100-epoch retrain, CLEAN val — QUOTE THIS** | **0.777** | **0.650** | **0.721** | **0.542** |

Talking point: clean val is *higher* than original val, so the detector eval was
not inflated by leakage (the quarantined images were hard scenes). The test-split
drop to 0.474 is honest evidence of batch-level domain shift on truly unseen
capture sessions, and pairs with the tiny-object limitation.

### Supporting evidence
- Confidence operating point: precision tunable 0.76 -> 0.92 by conf threshold
  (`runs/detect/precision_threshold_sweep/`).
- Cross-domain honesty: features trained on studio images drop ~40pp on real-world
  images (`runs/dl/cross_dataset_validation/`) — motivates the DL branch + field data.
- Failure analysis: recall is limited by tiny objects (organic median box ~1.4% of
  image, 53% missed), not by class confusion (<=11%).

## 3. The verification story ("how do you check it worked?")

Say it in this order:

1. **Reproducible scripts, versioned**: every experiment is a script in `scripts/`,
   every result a folder in `runs/`, all committed to GitHub
   (github.com/khoaph0712/Final-Year-Project-PDK) with dated history. Anyone can rerun:
   audit, evals, training - same numbers come out.
2. **We audited our own evaluation**: `scripts/audit_model_risks.py` hashed all ~79k
   images (MD5 + perceptual dHash) and checked leakage, bias, label noise, pseudo-labels,
   overfitting. It FOUND a real bug: 43% of the classifier test set duplicated training
   images (same photos entering via TACO-official and Roboflow re-exports).
   Visual proof: `runs/audits/near_dup_spotcheck.jpg`.
3. **We corrected our numbers**: quarantined every leaked eval image
   (`runs/audits/quarantine_manifest.csv`), re-evaluated, and now report 91.77%
   instead of the inflated 94.30%. The failure log for the report is
   `docs/01_final_report/FAILURES_AND_FIXES.md` (8 documented failures with root
   causes and fixes).
4. **Independent checks**: self-tests in the audit tool (known-duplicate positive
   control, unrelated-image negative control), confusion matrices, per-class reports,
   and a live web demo on images the model has never seen.

Key sentence for the teacher:
> "My numbers are lower than my first report because I found and fixed an evaluation
> bug myself - the corrected numbers are the ones I stand behind, and here is the
> audit trail that proves it."

## 4. Likely questions + answers

- **"Why did accuracy go DOWN?"** - It didn't; the measurement got honest. 94.3% was
  measured on a test set that contained training photos. 91.77% is the same model on
  clean data. Detecting this is a result in itself.
- **"How do I know you ran this yourself?"** - GitHub commit history with dates,
  run artifacts with timestamps in `runs/`, and I can rerun any script live.
- **"Why two stages instead of just YOLO?"** - YOLO finds objects well (IoU 0.90) but
  material ID from crops is stronger with a dedicated classifier (91.8% honest);
  each stage does what it is best at. Evidence: confusion matrix shows YOLO's errors
  are misses, not misclassifications.
- **"What is the biggest remaining weakness?"** - Tiny objects (organic litter):
  median object is ~74px at 640 input; 53% are missed. Next step is a 960px training
  run; measured plan, not hand-waving.
- **"Is the dataset trustworthy?"** - Audited: no pseudo-labels (all human
  annotations), splits source-aware, 0 corrupt images after cleanup; the one real
  issue (cross-source duplicates) was found and quarantined by us.
